# API-driven IOMR implementation report

Baseline: main commit `9a15bf0d214482931f66c880384ee2d5f222f7d3` (SCL 0.3.0).
Candidate: 0.4.0-rc.1 / Python package 0.4.0rc1. Metamodel: unchanged at iomr-evolved 2.0.0.

## Implemented architecture

`ModelService.execute` is the reusable JSON application contract. The CLI `api`
commands and 23 named stdio MCP tools call it. Domain candidate application and
validation live in `domain.py`; the existing structural validator remains central.
`Storage` abstracts persistence and `JsonStorage` supports legacy/custom directories,
split files, deterministic serialization, ownership preservation and path containment.
No database or HTTP server was introduced.

Discovery includes focused context, metamodel and exact API schemas, record search,
record lookup, traces, dependants and revisions. Coherent changes support additions,
updates, relationship additions/removals, retirement/supersession and source declarations.
Semantic helpers create identities and parent links automatically. Complete transactions
may contain new models, new participants, constraints and links without intermediate validity.

## Approval, integrity and publication

Proposals remain separate from canonical arrays. Candidate validation checks the whole
graph plus the existing framework/behaviour gates for framework checkouts. Skill discovery
still gates significant operations. Validation never grants approval.

Detached SSH signatures bind the reviewer, proposal content, prior revision and resulting
file hashes, including evidence and generated documents. Allowed signers come from an
externally administered file. No signing keys are loaded or generated by the product.
Default operation is proposal-only. Original inference, basis, status, evidence, author
claim, prior record digest and reviewer remain in provenance; approved inferred records
project to derived basis. The unsafe legacy `integrate_slice` writer now fails closed.

Optimistic revisions and OS locks prevent cooperative lost updates. Prepared JSON and
documents use an undo journal, per-file replacement and recovery. Rollback includes the
proposal and receipt. POSIX readers share a lock. This is recoverable multi-file writing,
not filesystem-wide atomicity; external readers/writers that ignore the lock remain a
limitation. Complete changes should be published in one guarded Git commit/ref update.

The trusted verifier checks signed transition continuity, verifies proposal digests,
replays reviewed operations in a fresh data-only workspace using trusted code, then
validates the final graph and generated documents. It rejects direct canonical edits,
forged receipts and signed file maps inconsistent with the reviewed operations. Candidate
code is never imported. Evidence cannot alias mutable outputs or service state.

## Compatibility and intentional changes

Existing `imk`/`scl`, framework/strict validation, release validation, consumer manifests,
Cairn export/check/proposal, role narratives, Mermaid exports and independent read-only
exports remain. Model-location discovery and generated source labels now respect consumer
configuration. Historical v0.1.0–v0.3.0 release snapshots are unchanged.

Intentional changes: `integrate_slice` raises `approval.required`; use `import_slice`,
complete the proposal and obtain verified review. Relationship ids now must be present
and unique. Retired records cannot be modified through the service. Source evidence
cannot point at mutable canonical outputs or internal service state. A new source can be
declared without hand-editing configuration, but changing an existing source or arbitrary
storage migration requires a new source version or explicit administrator baseline migration.

## Prepared but not authorised or activated

1. **Self-model integration:** proposal `proposal-c62f6d6c2c6a837f93e3d620` is valid but
   unsigned. It reuses existing Intents, Outcomes and participants, adds two interaction
   Models, ten requested Requirements and one explicitly inferred SSH-review Decision.
   Views in `internal/api-model-preview` are labelled pending. The canonical model is
   valid and unchanged; no human model approval has been invented.
2. **Hosting enforcement:** the GitHub trusted-base workflow and GitLab policy template
   are implemented. An administrator must provision reviewer keys, activate required
   checks and protect the branch/trusted code. The first PR is a reviewed trust bootstrap;
   its base does not yet contain this checker. GitLab needs a separately protected policy
   job or external required check. Local filesystem writes are not technically prevented.
3. **Release:** a reproducible 0.4.0 candidate, change notes, upgrade guide and validation
   checklist are prepared under `release-candidates/v0.4.0`. No final release, tag or
   package is published. Human release approval is still required after reviewing the
   final model and candidate bytes.
4. **Deferred scope:** HTTP hosting, remote identity providers, databases, arbitrary
   metamodel execution and a fully atomic Git-backed publication adapter. The current
   service exposes extension boundaries without claiming these are implemented.
